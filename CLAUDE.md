# Themes Workspace

Design workspace for Typora and Obsidian themes built from nine palettes: TokyoNight
(`tn-`), Catppuccin (`cp-`), Merino (`mr-`, after the Merino Light/Dark terminal themes — GitHub
Primer colors), Big Wave (`bw-`, after the cover of Tatsuro Yamashita's "Big Wave"), Impression
(`im-`, after Monet's "Impression, Sunrise"), Bauhaus (`bh-`, the three primaries, solid blocks,
square corners), Shanghai (`sh-`, the two banks of the Huangpu), Tuttomondo (`tm-`, after the 1989
mural in Pisa: outlines, hard shadows, color in blocks) and Wonderland (`wl-`, original, inspired by Murakami's "Hard-Boiled Wonderland").
A new palette is just a new `shared/palettes/<palette>.toml` (plus its name in
`shared/lamplit.toml` → `schemes`); the generator does the rest. The file name is the palette
slug and shows up in Typora's menu, so use hyphens between words (`big-wave` → "Big Wave").
- **Obsidian**: one theme, **Lamplit** (`ll-`), carrying every palette as a Style Settings
  scheme (dark scheme and light scheme chosen separately).
- **Typora**: one theme file per palette variant, also under the Lamplit name
  (`lamplit-tokyonight-storm.css` → "Lamplit Tokyonight Storm" in Typora's menu).

Status, to-dos and current versions live in `THEMES_PLAN.md` — keep it updated when work lands.

## All theme files are GENERATED — never edit them by hand

`obsidian/lamplit/theme.css`, `obsidian/lamplit/manifest.json` and `typora/<palette>/*.css`
are generated by `./scripts/gen-themes.py` from:

- `shared/palettes/<palette>.toml` — variants and their colors, color roles (accent, search,
  headings, tag, …), style switches (`nav_style` / `menu_style`: `tint` | `fill`; `corners`:
  `round` | `square`; `mark_style`: `tint` | `solid`; `outline`: `none` | `bold`; `shadow`: `none` |
  `hard` — omitted = the original look), the
  Typora version, and `short_name` (the label in Lamplit's scheme dropdowns)
- `shared/lamplit.toml` — Lamplit's name, prefix, Obsidian version, default dark/light
  scheme and the palette order in the dropdowns
- `scripts/templates/obsidian.css.tmpl` and `scripts/templates/typora.css.tmpl` — the CSS
  shared by all palettes (placeholder syntax is documented at the top of `gen-themes.py`)

Workflow: edit the TOML (colors, roles, versions) or a template (structure, a fix for all
themes), run `./scripts/gen-themes.py`, then sync. `--check` exits 1 if outputs are stale.
A theme-specific difference belongs in the TOML as a role or style switch, not as a
one-off edit in a generated file. When refactoring a template, diff the generated CSS
against the previous version rule by rule (resolved values per variant) before committing,
and run the Obsidian verification below — a CSS diff cannot see how a rule interacts with
app.css (e.g. a link rule that silently recolored `a.tag`).

## Directory layout

```
themes/
├── obsidian/lamplit/        # theme.css + manifest.json (generated) + README.md, screenshot.png, palettes.png
├── typora/<palette>/        # lamplit-<palette>-<variant>.css (one file per variant), screenshot.png,
│                            # README.md + README.zh-CN.md (every README has a Chinese twin: change both)
├── shared/
│   ├── lamplit.toml            # Lamplit settings — see above (its name is also the Typora prefix)
│   ├── palettes/<palette>.toml # SOURCE OF TRUTH per palette (see above)
│   └── tokens/base.css         # reference values only — NOT imported by any theme
├── scripts/
│   ├── gen-themes.py        # generates every theme file (--check to verify)
│   ├── templates/           # obsidian.css.tmpl, typora.css.tmpl
│   ├── verify-obsidian/     # automated Reading/Live Preview rendering check (see Obsidian)
│   ├── sync-obsidian.sh     # ./scripts/sync-obsidian.sh <vault-path> [theme]
│   ├── sync-typora.sh       # ./scripts/sync-typora.sh [theme]
│   ├── package-release.sh   # builds the release archives into dist/ (git-ignored)
│   └── publish-lamplit.sh   # publishes the theme to agiledolphin/lamplit
├── .verify/                 # verify-obsidian output (git-ignored)
├── install.sh               # installs from the latest GitHub Release, no clone needed
├── README.md                # overview, installation (keep palette table and counts current)
├── README.zh-CN.md          # Chinese version; change it together with README.md
├── LICENSE
└── THEMES_PLAN.md
```

Every theme file is self-contained (no `@import`): Obsidian loads a single `theme.css`, and
Typora files are copied flat into Typora's themes directory, so relative imports would break.

## Obsidian (Lamplit)

- Style Settings: `ll-dark-scheme` (every dark variant of every palette) and `ll-light-scheme`
  (every light variant), class values `ll-<palette prefix>-<variant>` (e.g. `ll-cp-latte`),
  plus `ll-hide-folder-icons`, `ll-hide-file-icons`, `ll-color-folders` and `ll-default-mermaid`.
  These ids are users' saved choices — never rename them.
- One block per variant: `body.theme-dark.ll-wl-office { … }` (the default variant's block also
  matches plain `body.theme-dark`). Each block defines the semantic variables the rules use
  (`--ll-accent`, `--ll-h2`, `--ll-search-rgb`, …); the generator turns every template
  placeholder into such a variable. Dark blocks MUST sit on `theme-dark` — app.css applies
  light-mode rules (e.g. `mix-blend-mode: darken` on callouts) to `theme-light`.
- Style-dependent template blocks (`{{#nav_style=fill}}…{{/nav_style}}`): whole rules are
  emitted for every style and scoped with `:where(<variants using that style>)` so their
  specificity is unchanged (the Catppuccin nav-hover rules depend on matching app.css exactly);
  declaration-only blocks move into the variant blocks; inline alternatives become
  `--ll-cond-N` variables. Without Style Settings the default (tint) style applies.
  Rule groups no variant uses are dropped. `mark_style = "solid"` makes only the mark
  elements solid: `--text-highlight-bg` stays the faint tint, because Obsidian reuses it
  (link flashes, search) under normal text. `corners = "square"` also zeroes Obsidian's own
  UI radii (`--radius-s/m/l/xl`, `--input-radius`, `--tab-radius-active`). `outline = "bold"` frames
  code, callouts, tables, tags, menus and modals in `outline_color` and makes tags solid; Live Preview
  draws inline code from `--code-border-*`, so those are set on the inline-code element too.
  `shadow = "hard"` puts unblurred offset shadows on callouts, tables, menus and modals, not on code
  blocks: Live Preview builds them from one element per line, so only Reading view could show one.
  The verification compares the frame and shadow of callouts, tables and tags between the views
  (`calloutFrame`, `tableFrame`, `tagFrame`); menus and modals are not measured.
- `ll-color-folders` colors top-level folders by `:nth-child`; children inherit `--ll-folder-color`.
  The 8 colors are `FOLDER_CYCLE` in `gen-themes.py`. Known limit, measured: the file explorer
  virtualizes, so scrolled-out top-level folders leave the DOM and the rest renumber (Blue Topaz's
  by-order mode does the same).
- Mermaid: since 1.15 Obsidian draws diagrams with Pele, whose colors come from the `--mermaid-*`
  variables, so the template only maps those (and `ll-default-mermaid` skips the mapping). Lamplit's
  `minAppVersion` is older, so the rules for Mermaid itself stay, all nested under one `{{MM}}` block
  (an app without CSS nesting ignores it). `{{MM}}` expands to a selector limited to `MERMAID_TYPES`
  in `gen-themes.py`, skips Pele's output with `:not(.pele)`, and its `:not(#_)` outranks Mermaid's
  id-scoped rules. The verification measures Pele only, with one section per diagram type in the test
  note (`MERMAID` in `pagelib.js`, built on Pele's class names). To check the Mermaid rules, start a
  temporary instance (`--user-data-dir`) without the update's `obsidian-<version>.asar`: it runs the
  installer's version.
- Obsidian's own palette is mapped too: `--color-red` … `--color-pink` (+ `-rgb`) to the scheme's
  colors (purple and pink both to magenta), and `--accent-h/s/l` from the accent (`accent_h/s/l`,
  computed in `gen-themes.py`), so colored highlights (`==🔴…==`), canvas cards, Sync avatars,
  state colors and every `--color-accent` use follow the scheme. Plain `==mark==` rules skip colored
  ones (`[data-highlight]` with a value, `.cm-highlight-<color>`); Reading view gives a plain one an
  empty `data-highlight`. The graph reads `--graph-line`, `--graph-node*`, `--graph-text`. Canvas:
  `--canvas-color` (uncolored cards, connectors) is the comment color, the dots the gutter. Obsidian's
  grey scale `--color-base-*` stays: Lamplit overrides everything app.css derives from it.
  To find what still ignores the scheme, compare every color variable's computed value under
  Lamplit with the default theme in a temporary instance: equal values are untouched.
- Below the variant blocks, one `body.theme-dark, body.theme-light` block maps the semantic
  variables onto Obsidian's own variables. Prefer setting Obsidian variables over styling a
  selector: Reading view and Live Preview often read the same variable through different
  selectors (`--blockquote-*`, `--code-border-width`/`--code-radius`, `--hr-*`,
  `--table-text-size`, `--tag-*`), while a theme rule on `.markdown-rendered …` reaches
  Reading view only and is often beaten in Live Preview by a higher-specificity app.css rule.
- When the two views differ and no variable covers it, prefer Obsidian's default over a
  theme override that only one view honors (done for tag size and inline-code padding).
- A theme rule can also collide with app.css in the same view: `.markdown-rendered a` has
  the same specificity as app.css's `a.tag` and loads later, so link rules must exclude tags
  (`a:not(.tag)`).
- `--ll-<name>-rgb` vars and `--callout-color` hold bare RGB triples (`195, 154, 95`)
  for `rgba()`. Wherever app.css uses such a var as a plain color, wrap it: `rgb(var(...))`.
- When a color doesn't apply, check what app.css actually does: extract it with
  `npx asar extract /Applications/Obsidian.app/Contents/Resources/obsidian.asar <dir>` and grep.
- Sync to the user's vault for testing: `./scripts/sync-obsidian.sh ~/notebook`. Obsidian silently
  skips a theme unless its folder name equals the manifest's `name` exactly (case-sensitive), so
  the script names the folder `Lamplit` from the manifest, and renames a lowercase `lamplit`.
- Automated check of the real rendering (after any Obsidian-side change):
  1. Obsidian running on a debug port (quit it, then
     `open -a Obsidian --args --remote-debugging-port=9333`), Lamplit synced to the vault.
  2. `node scripts/verify-obsidian/run.mjs` — every scheme from the TOMLs, ~10 min
     (`--only cp-latte,wl` and `--sections mermaid,tables` to narrow; `--note <vault path>`, default
     `tech/lab/obsidian/obsidian-theme-sample.md`; `--port`, `--out`).
  3. `uv run scripts/verify-obsidian/analyze.py .verify [--baseline <earlier run>]` — every
     Reading/Live mismatch, contrast per variant, Mermaid (every diagram type rendered without the
     inversion filter, solid and hollow markers, any painted color not from the scheme; text on
     its fill below 3:1 is reported), colored highlights (each measured, none the plain mark's or
     another's color), and with `--baseline` every difference from
     an earlier run (styles, mapped Obsidian variables, UI probes incl. forced :hover); exit 1
     on any. Writes `.verify/index.html` with screenshots. For a refactor: copy `.verify` to
     `.verify-baseline` first, then compare — a refactor must show 0 differences.

  Choose the scope from what changed; a full run is the exception. A narrowed run writes to
  `.verify-scoped`, so compare it with `analyze.py .verify-scoped --baseline .verify`:
  - one palette's TOML: `--only <its variants>`
  - a template rule for one area: `--only bw-pipeline,wl-lab` (a dark and a light scheme, plus
    `cp-latte` when colors change) with `--sections` for that area
  - a style switch: `--only` the variants using it plus one that does not
  - verification tool or test note only: one scheme, the affected sections
  - full run: a change to the generator, the variant blocks or the Obsidian variable mapping, a
    refactor (must show 0 differences), or an Obsidian update

  Keep Obsidian's window visible for the whole run: while it is minimized, covered or on
  another Space, Chromium stops rendering (no animation frames), lazily rendered content never
  appears and measurements would come back empty — the tool checks this and refuses (exit 3). Measured, not adopted: with
  `setBackgroundThrottling(false)` and focus emulation a covered window keeps rendering, but a
  minimized one never returns a fresh screenshot.
  It switches schemes on screen (tell the user before running it), works in a new tab plus
  off-screen probe elements, never edits the note, and restores the user's theme, mode and
  Style Settings classes. Each run clears its own previous output, only after connecting.
  Live Preview table drag handles can't be triggered this way — check by hand.

## Typora

- Themes directory: `~/Library/Application Support/abnerworks.Typora/themes/`
- One standalone CSS file per variant, named `lamplit-<palette>-<variant>.css` (Typora's menu
  shows the file name: prefix from `shared/lamplit.toml` `name`, palette from `short_name`); the palette is
  declared in that file's `:root`. `--bg-color` must be set in `:root` (it drives `#write`).
- After syncing, reselect the theme in Preferences → Appearance (or restart Typora).

## Design conventions

- All colors go through CSS custom properties; never hardcode a hex outside the palette blocks.
- Chinese body text: PingFang SC → Hiragino Sans GB → Noto Serif SC.
- One step below body text is `--font-smaller` (0.875em, 14px at 16px) — used for code, tables,
  tags and footnotes alike; inline code inside table cells stays at cell size (1em).
- Tables size to their content (no `width: 100%`), cells padded 6px / 12px on both platforms.
- Typora content width ≤ 860px (960px on ≥1400px screens).
- Text contrast: accents ≥ 4.3:1 against the background, faint text (H6, comments, unresolved
  links) ≥ 3:1 — the thresholds `analyze.py` reports against. Some upstream palettes (TokyoNight
  Day, Catppuccin Latte) fall below in places; those are recorded in `THEMES_PLAN.md`, not
  silently changed.

## Versioning & commits

- Versions: Lamplit's in `shared/lamplit.toml` (`obsidian_version`, written into its
  `manifest.json`), each palette's Typora version in its TOML (`typora_version`, written into
  the Typora file headers). Bump only what changed rendering (patch for fixes, minor for
  feature batches) and update the table in `THEMES_PLAN.md`. A pure refactor that renders
  identically does not bump.
- Commit style: `feat(obsidian): …`, `fix(typora): …`, `docs: …`, `chore: …`.
- Releases: `install.sh` and the README download from the latest GitHub Release, so theme changes
  reach users only when released. After pushing, run `./scripts/package-release.sh`, then the
  `gh release create v<Lamplit version> dist/*.zip …` it prints (ask the user first: it publishes).
  The tag follows Lamplit's version. A Typora-only change has no new Lamplit version: replace the
  archives on the current release with `gh release upload v<version> dist/*.zip --clobber`.
- Obsidian community directory: it reads `agiledolphin/lamplit`, a publish-only repository with
  the theme files in its root. `./scripts/publish-lamplit.sh` copies them from here and creates
  the release; its tag must equal the manifest's version, with no `v`. Run it for every new
  Lamplit version (ask the user first: it publishes), and never edit that repository directly.
  Its READMEs and images are in `obsidian/lamplit/` (`README.md`, `README.zh-CN.md`, `screenshot.png`,
  `palettes.png`);
  the directory reads those from the main branch, so `--docs` publishes them without a release.

## Tooling

- Run Python through uv, never a bare `python3`: `uv run <script>`, and
  `uv run --no-project python -c …` (or `python -` with a heredoc) for one-off snippets.
  Repo scripts carry `#!/usr/bin/env -S uv run --script` plus PEP 723 inline metadata
  (`requires-python = ">=3.11"`, needed for `tomllib`), so `./scripts/gen-themes.py` already
  goes through uv; new Python scripts follow the same pattern.
- The verification scripts are Node (≥ 22, for the built-in `WebSocket`) + uv/Python; no
  package installs are needed.
